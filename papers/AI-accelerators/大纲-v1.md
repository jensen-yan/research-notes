# 从 Cache 到 Dataflow：AI 加速器的数据移动趋势与 XSAI/AME 的位置

## 目标

面向同组人员做一次 25-35 分钟技术分享，主题不是泛泛介绍 GPU/TPU，而是用最近阅读的论文和笔记串出一个判断：

> AI 加速器的核心矛盾，已经从“有没有足够算力”转向“数据能不能在正确时间、以正确粒度、停留在离计算单元足够近的地方”。

最后用 2-3 页回到 XSAI/AME：当前 XSAI 是“大 OoO core + CUTE 类 tensor core + shared L2”的早期 AME 路线，还没有 scratchpad 模式、独立 vector/reduction 模块和完整 dataflow 软件栈。它是合理起点，但后续是否加入 scratchpad、DMA、vector 模块和更多 AME 指令，应由 workload 与 gem5 建模结果决定。

## 推荐风格

- `guizang-ppt-skill` 风格 B：瑞士国际主义。
- 推荐主题色：IKB 蓝。
- 原因：这次内容是架构判断、对比表、数据流图和技术路线，不适合杂志叙事风；瑞士风更适合信息密集型分享。

## 叙事弧

1. Hook：现代 AI 芯片缺的不是 MAC，而是喂饱 MAC 的数据路径。
2. Context：Transformer/LLM 把问题变成大块 tensor 计算 + decode 动态系统问题。
3. Core：Roofline、DNN survey、DianNao、GPU/TPU、Triton/Pallas/Timeloop 共同指向 data movement。
4. Shift：GPU/TPU 看似两条路线，但都在承认数据移动必须显式化、编译器化。
5. Takeaway：XSAI/AME 的关键不是“多一个矩阵单元”，而是矩阵状态、数据路径、CPU 协同和软件调度边界。

## Slide 2. Hook：缺的不是 MAC，是喂饱 MAC

### 标题

The Bottleneck Moved

### 核心句

当矩阵单元越来越大，真正困难的是让数据持续、准时、低成本地到达计算单元。

### 内容要点

- MAC / Tensor Core / MXU 数量可以堆，但 DRAM/HBM 带宽和片上数据组织跟不上。
- 数据搬运通常比算术本身更贵。
- 对 AI workload，很多访问模式是规则的，因此可以提前规划。

### 视觉

一张极简流程图：

```text
DRAM/HBM -> L2/SRAM -> Scratchpad/VMEM -> RF/Tensor Core
          cost high       cost medium       cost low
```

## Slide 3. Transformer 改变了硬件问题

### 标题

From Sequence to Tensor

### 核心句

Transformer 把训练和 prefill 的大部分工作变成可并行矩阵计算，但 decode 仍然带来低 batch、KV cache 和动态控制问题。

### 内容要点

- Attention 让 token 间关系可以用矩阵计算表达。
- Prefill：输入 token 已知，可以较大程度并行。
- Decode：逐 token 自回归，时间维度串行。
- LLM serving 不是纯 GEMM，而是 GEMM + KV cache + vector/reduction + scheduling。

### 视觉

表格：

| 阶段 | 主要操作 | 硬件特征 |
|---|---|---|
| Prefill | Attention / FFN / GEMM | 高并行、高复用 |
| Decode | GEMV / KV cache read / sampling | 低 batch、访存重、动态控制 |

## Slide 4. Roofline：第一性约束

### 标题

Compute Is Only Half the Roof

### 核心句

Roofline 的价值是把一个 kernel 的瓶颈压成两个问题：算力够不够，数据搬运够不够。

### 内容要点

- 横轴：Operational Intensity，Flops / DRAM Byte。
- 纵轴：可达到性能。
- ridge point 决定 kernel 至少需要多高数据复用才能吃满峰值算力。
- 同一个 kernel，在不同 memory hierarchy 下有效 OI 会不同。

## Slide 5. 数据搬运是 DNN 加速器的一等公民

### 标题

Memory Transfer Became the Workload

### 核心句

DNN 加速器的本质不是“做很多 MAC”，而是围绕 layer shape 设计 memory hierarchy、dataflow、precision 和 sparsity。

### 内容要点

- DNN 能耗很大一部分来自 off-chip DRAM，而不是 MAC。
- row-stationary / weight-stationary / output-stationary 等 dataflow，本质是在选择哪些数据留在近端。
- 降低精度、剪枝、MoE，也都可以理解为减少有效搬运或提高单位 byte 的计算量。

## Slide 6. Temporal vs Spatial

### 标题

Two Ways to Feed ALUs

### 核心句

Temporal 架构依赖硬件动态机制隐藏延迟；Spatial 架构让数据在 PE 附近停留并在 PE 间流动。

### 内容要点

- Temporal：CPU/GPU 更典型。ALU 从寄存器/cache 层次取数据，计算，再写回。
- Spatial：NPU/TPU 更典型。PE = compute + local state + control/data movement。
- Spatial 的收益来自数据复用更靠近计算单元。
- 代价是灵活性下降，需要 shape / mapping / compiler 配合。

### 视觉

左右对比图：

```text
Temporal:
Cache/RF -> ALU -> Cache/RF
硬件负责猜局部性、隐藏延迟

Spatial:
PE <-> PE <-> PE
数据边流动边被消费
```

- `DNN-survey.md`
- `TPU.md`

## Slide 7. DianNao：早期答案已经出现

### 标题

Before TPU, There Was Scratchpad

### 核心句

DianNao 很早就指出：对规则 DNN 访问，通用 cache 的 tag、associativity、speculative read 和 conflict 可能变成额外成本。

### 内容要点

- DianNao 用 NFU + NBin/NBout/SB + DMA 组织前向推理。
- 它不依赖传统 cache，而是用软件管理 buffer / scratchpad 保存输入、权重和部分和。
- DMA 预取相当于非投机 prefetch：提前把确定会用的数据搬到近端。

## Slide 8. Systolic Array：数据在 PE 间流动

### 标题

Data Moves, Compute Stays

### 核心句

脉动阵列的关键不是“有很多 MAC”，而是 A/B 数据在二维 PE 阵列中逐拍传播，经过哪里就在哪里被消费。

### 内容要点

- 矩阵乘：`C[i][j] = sum_k A[i][k] * B[k][j]`。
- A 沿行传播，B 沿列传播。
- 一个 A 元素被同一行多个 PE 复用，一个 B 元素被同一列多个 PE 复用。
- PE 不需要复杂指令调度，面积更多留给 MAC。

### 视觉

```text

     PE PE PE
B    PE PE PE
v    PE PE PE
v
```

## Slide 9. GPU 路线：从 SIMT 到显式数据移动

### 标题

GPU: Threads First, Dataflow Later

### 核心句

GPU 从线程灵活性出发，但 A100/H100/B200 的演进越来越强调把数据移动显式化。

### 内容要点

- GPU 基本抽象：threads -> warps -> blocks -> clusters -> grid。
- A100：`cp.async`，把 global memory 直接搬到 shared memory。
- H100：TMA、WGMMA、mbarrier、thread block cluster、DSMEM。
- B200：TMEM、tcgen05，让 tensor compute 与 warp 调度进一步解耦。
- 趋势：数据移动不再是副作用，而是程序本身。

### 视觉

时间线：

```text
A100: cp.async
H100: TMA + WGMMA + mbarrier + DSMEM
B200: TMEM + decoupled tensor compute
```

- `GPU-vs-TPU(hardware).md`

## Slide 10. TPU 路线：从第一天起押注编译器

### 标题

TPU: Dataflow First

### 核心句

TPU 放弃很多动态机制，用 MXU、VMEM 和编译器调度 DMA 换取密度、确定性和规模化。

### 内容要点

- TPU 核心模块：MXU、VPU、scalar control、VMEM、HBM、ICI。
- 没有传统硬件管理的 L1/L2 cache。
- 编译器负责 HBM -> VMEM -> MXU/VPU regfile 的数据路径。
- 优势：吞吐密度、确定性、规模化互联。
- 代价：shape 不合适、batch 太小或动态行为多时，可能 padding/waste/fallback。

## Slide 11. GPU 和 TPU 正在收敛

### 标题

Different Roads, Same Wall

### 核心句

GPU 越来越显式地管理数据流；TPU 一开始就把数据流交给编译器。两者都在承认：data movement 是架构一等公民。

### 内容要点

- GPU 添加更近计算的 memory：SMEM、DSMEM、TMEM。
- GPU 添加显式搬运：cp.async、TMA。
- GPU tensor compute 与 warp scheduling 越来越解耦。
- TPU 继续强化 VMEM、MXU、编译器和互联。
- 共同目标：让数据尽量长时间停在计算附近。

### 视觉

二列表：

| GPU 趋势 | TPU 起点 |
|---|---|
| 从 SIMT 灵活性出发 | 从矩阵 dataflow 出发 |
| 逐步显式化数据移动 | 编译器一直调度数据移动 |
| 加近端 memory | VMEM 是核心层 |
| 兼顾生态和 escape hatch | 追求确定性和规模化 |

### 来源

- `GPU-vs-TPU(hardware).md`

## Slide 12. Tile 是现代 AI 编程的核心抽象

### 标题

Think in Tiles

### 核心句

Tile 不是完整矩阵，也不是 thread/lane 指令，而是能表达数据复用、片上存储和矩阵单元使用的中间抽象。

### 内容要点

- 太高层：matmul / attention / conv，表达简单但不够可控。
- tile 层：固定形状的数据块，可以描述复用、layout、pipeline。
- 太底层：thread / lane / instruction，控制强但程序员负担大。
- 现代 AI workload 大量操作都是 matrix、attention、norm、activation、reduction，访问模式相对规则。

### 视觉

三层抽象阶梯：

```text
Operator: matmul / attention
Tile: 128x128 / BlockSpec / BLOCK_M,N,K
Instruction: mma / wgmma / load / barrier
```

- `GPU-vs-TPUP(software).md`

## Slide 13. 软件栈成为架构的一部分

### 标题

Compiler as Architecture

### 核心句

Triton、Pallas、Mosaic 的意义在于：程序员描述 tile 和数学，编译器决定 layout、DMA、同步和指令打包。

### 内容要点

- Triton：同一份 tile kernel，可在不同 GPU 上生成不同实现。
- Pallas：`BlockSpec` 描述 HBM 到 VMEM 的 tile。
- Mosaic：决定 VMEM vs register、tile shape、DMA scheduling。
- LLO/VLIW：把 scalar、vector、DMA 等互不冲突的动作打包。
- 编译器越强，硬件动态调度可以越少；但成本是编译复杂度和 escape hatch 变少。

### 视觉

管线图：

```text
Python/JAX/PyTorch
-> HLO/StableHLO
-> Pallas/Triton tile kernel
-> Mosaic/PTX/backend
-> DMA + MMA + barrier + layout
```

## Slide 14. Timeloop：mapping 决定硬件是否真的快

### 标题

Same Hardware, Different Mapping

### 核心句

同一个硬件，在不同 tiling、loop order、dataflow 和 bypass 策略下，性能和能耗可能差很多。

### 内容要点

- Timeloop 输入：硬件描述、workload、mapping constraints。
- mapping 决策：tiling、loop permutation、spatial partitioning、temporal scheduling、bypass、dataflow constraints。
- 性能/能耗模型本质是结构化 roofline / bottleneck model。
- 它不是 cycle-accurate simulator，但适合解释规则 DNN loop nest。
- 对 AME 的启发：建模不能只写“矩阵单元每周期多少 ops”，还要建数据如何被搬、复用和等待。

## Slide 15. LLM Serving：不是纯 GEMM 世界

### 标题

Prefill Loves Matrix, Decode Loves Systems

### 核心句

Prefill 更像规则大矩阵计算，decode 更像低 batch GEMV + KV cache + 动态控制，因此加速器必须和 CPU/系统调度协同。

### 内容要点

| 模块 | 主要操作 | 并行性 | 数据特征 | 更适合 |
|---|---|---|---|---|
| Prefill FFN/GEMM | 大矩阵乘 | 高 | 复用高 | AME / Tensor Core |
| Prefill Attention | QK/AV + softmax | 中高 | tile + reduction | AME + vector |
| Decode GEMV | 小 batch matvec | 中低 | 权重读多 | 特化 AME 或 vector |
| KV cache | read/write/gather | 低 | 容量和带宽敏感 | cache/memory system |
| Sampling/routing | control-heavy | 低 | 不规则 | CPU |

## Slide 16. 回到 XSAI：当前站在哪里

### 标题

XSAI Today: OoO + CUTE + Shared L2

### 核心句

当前 XSAI 更像 CPU 紧耦合矩阵扩展的起点：大 OoO core 搭配 CUTE 类 tensor core，共享 L2Cache，但还没有完整 scratchpad/dataflow 软件栈。

### 内容要点

- 大 OoO core：负责控制流、通用程序、低延迟调度。
- CUTE 类 tensor core：负责矩阵主干计算。
- 共享 L2Cache：当前主要数据供给路径。
- 暂无独立 scratchpad 模式。
- 暂无独立 vector/reduction 模块。
- 当前 AME 指令较少，后续可以扩展 load/store、sync、layout、format convert、reduction 等。

## Slide 17. AME vs IME：不是名字之争

### 标题

Where Does Matrix State Live?

### 核心句

AME 和 IME 的关键差异，不只是 ISA 语义，而是矩阵状态放在哪里、由谁供数、近端存储和软件调度能做到什么程度。

### 内容要点

| 路线 | 矩阵状态 | 优势 | 主要约束 |
|---|---|---|---|
| RVV | vector registers | 通用、生态连续 | 指令数多，矩阵复用弱 |
| IME | vector RF + matrix FU | ISA 连续性好 | VRF 容量、load bandwidth、端口压力 |
| AME | 独立矩阵状态/矩阵单元，可扩展 local buffer | 更容易围绕矩阵重做数据路径 | matrix/vector 边界、一致性、软件栈 |

### 关键表达

> RVV 是拿向量拼矩阵。IME 是矩阵语义进入 ISA，但矩阵还住在 RVV 寄存器里。AME 则更容易让矩阵自己有房子、有路、有厨房。

### 讲述重点

- IME 并不天然逃过数据移动问题。
- SpacemiT K3/A100 这种 IME-like 高性能方案，最后也会碰到超宽 VRF、load channel、多个 core 供一个 tensor core、local memory、AI-DMA 和 async prefetch。
- 因此更本质的问题是：固定资源预算下，哪条路径能更低成本地把矩阵单元喂饱？

### 来源

- `AME-vs-IME.md`

## Slide 18. XSAI/AME 下一步要量什么

### 标题

Measure the Data, Then Add Hardware

### 核心句

当前 XSAI 的 AME 是合理起点；下一步不是先把结构做复杂，而是用 gem5 把数据到底卡在哪里量出来。

### 内容要点

需要验证的问题：

- 共享 L2 模式能否满足 CUTE 的供数需求？
- batch=1 / 小 batch decode 是否被 KV cache 和 matrix/vector 边界主导？
- 是否需要 AME scratchpad/local memory？
- 是否需要 AME 侧 vector/reduction 模块处理 softmax、layernorm、RoPE、GELU/SiLU？
- 是否需要 DMA / async prefetch / software-managed tile movement？
- AME 指令是否要扩展到 load/store、sync、layout、format convert？

### 建模建议

gem5 里至少要统计：

- tile setup latency
- L2/AME load bandwidth
- CUTE utilization
- load stall / memory stall
- matrix/vector 边界搬运次数
- working-set residency
- CPU/AME 同步开销
- prefill 与 decode 分开统计

### 结论句

> AME 的价值不是替代 CPU，而是在 CPU 仍负责动态控制的前提下，把规则 tensor 数据流的重复搬运降下来。

## Slide 19. 结论

### 标题

Three Takeaways

### 核心句

AI 加速器的未来，是规则 tensor 流与动态 CPU 控制之间的协同边界设计。

### 三个 takeaway

1. **Data movement is the architecture.**  
   算力不是孤立指标，数据路径决定矩阵单元能不能被喂饱。

2. **Compiler/runtime is part of the machine.**  
   Tile、mapping、DMA、layout、sync 这些决策越来越前移到软件栈。

3. **XSAI/AME should evolve by evidence.**  
   当前 OoO + CUTE + shared L2 是合理起点；scratchpad、vector 模块、DMA 和更多指令，需要由 workload 和 gem5 数据推动。

### 视觉

三列大字报：

```text
DATA
COMPILER
AME EVIDENCE
```

## Slide 20. 讨论页

### 标题

Open Questions

## 需要新画的图

### 图 1. Cache 模式 vs Scratchpad 模式

目的：解释硬件猜局部性和软件显式声明局部性的区别。

```text
Cache mode:
CPU/AME -> L1/L2 -> Memory
hardware discovers locality

Scratchpad mode:
compiler/runtime -> DMA tile -> local memory -> tensor core
software declares locality
```

### 图 2. XSAI/AME 双路径数据流

目的：解释当前 shared L2 路线和未来 scratchpad 路线不是非黑即白。

```text
Path A: Memory -> AME scratchpad -> CUTE
        for large GEMM / prefill / regular tiles

Path B: Memory -> L2 -> OoO CPU + CUTE
        for decode / control-heavy / small batch
```

### 图 3. Prefill vs Decode 硬件映射表

目的：避免把 LLM 推理粗暴等同于“大矩阵乘”。

| 阶段 | 计算 | 数据 | 推荐执行侧 |
|---|---|---|---|
| Prefill FFN | GEMM | 高复用 | CUTE/AME |
| Prefill Attention | GEMM + softmax | tile + reduction | AME + vector |
| Decode | GEMV + KV | 低 batch、访存重 | CPU + AME 协同 |
| Sampling | control | 动态 | CPU |
