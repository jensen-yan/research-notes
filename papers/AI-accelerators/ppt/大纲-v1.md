# 从 Cache 到 Dataflow：给 CPU 背景同学的 AI 加速器入门与 XSAI/AME 思考

## 目标

面向组内传统 CPU / 微架构背景同学做一次 60 分钟左右技术分享。目标不是泛泛介绍 GPU/TPU 名词，而是帮助大家从熟悉的 CPU 直觉迁移到 AI 加速器的数据流直觉：

> CPU 的复杂动态机制，是为了让“未来很难预测”的通用程序跑得快；AI 加速器的主干优化，则越来越依赖“未来可以提前知道”的 tensor/tile 访问，把数据移动从硬件猜测变成软件/编译器显式编排。

最后回到 XSAI/AME：当前 XSAI 是“大 OoO core + CUTE 类 tensor core + shared L2”的 CPU 紧耦合 AME 起点。它不是完整 TPU-like dataflow 机器，也不该一开始就把 scratchpad、DMA、vector/reduction、复杂 runtime 全塞进去。正确路径是先用 workload 和 gem5 数据量清楚：矩阵单元是否被喂饱，数据是否反复穿越 L2，matrix/vector 边界是否成为瓶颈，再决定哪些 dataflow 能力值得引入。

## 推荐风格

- `guizang-ppt-skill` 风格 B：瑞士国际主义。
- 主题色：IKB 蓝。
- 理由：这次是工程入门 + 架构判断，内容包含对比、流程、系统图和概念迁移；瑞士风更适合信息密集型教学。

## 叙事弧

1. Hook：现代 AI 芯片缺的不是 MAC，而是喂饱 MAC 的数据路径。
2. Bridge：CPU 为什么需要分支预测、乱序、cache、prefetch、coherence？
3. Shift：AI 主干 kernel 的问题不是“未来不可预测”，而是“数据太大、复用太关键”。
4. Model：Roofline 把瓶颈压成两个问题：算力屋顶和带宽屋顶。
5. Core：从 cache 到 scratchpad/dataflow，本质是局部性管理者从硬件转向软件/编译器。
6. Evidence：DianNao、systolic array、GPU A100/H100/B200、TPU 都在不同路径上显式化数据移动。
7. Software：软件栈不只是调用库，而是在编排 tile、layout、DMA、barrier、MMA/MXU。
8. Back to us：XSAI/AME 的关键不是“有没有矩阵单元”，而是矩阵状态、数据路径、CPU 协同和软件暴露粒度。

## Slide 2. Hook：缺的不是 MAC，是喂饱 MAC

### 标题

The Bottleneck Moved

### 核心句

当矩阵单元越来越大，真正困难的是让数据持续、准时、低成本地到达计算单元。

### 内容要点

- MAC / Tensor Core / MXU 数量可以堆，但 DRAM/HBM 带宽和片上数据组织跟不上。
- 数据搬运通常比算术本身更贵。
- 对 AI workload，很多访问模式是规则的，因此可以提前规划。
- 这让我们从 CPU 的“隐藏延迟”问题，走向 accelerator 的“编排数据流”问题。

### 视觉

```text
DRAM/HBM -> L2/SRAM -> Scratchpad/VMEM -> RF/Tensor Core
         cost high       cost medium       cost low
```

## Slide 3. CPU 的敌人是不确定性

### 标题

CPU Optimizes for Unknown Futures

### 核心句

CPU 面对的是通用程序：分支多、指针多、地址运行时才知道、cache miss 不可预测、单线程延迟敏感。

### 内容要点

- Branch Predictor：猜下一条控制流。
- Out-of-Order：运行时寻找哪些 ready 指令可以先做。
- Cache：硬件观察访问历史，猜哪些 cache line 还会用。
- Prefetcher：根据地址模式猜未来访问。
- Coherence：在多核之间维护透明共享内存抽象。

### 讲述重点

CPU 很多面积和能耗不是在做算术，而是在让“不知道未来”的程序也跑得快。

### 视觉

五个竖向模块：

```text
Branch   OoO   Cache   Prefetch   Coherence
predict  reorder  discover  speculate  reconcile
```

## Slide 4. 乱序调度在隐藏什么

### 标题

OoO Is Runtime Scheduling

### 核心句

乱序不是魔法，它是在运行时寻找仍然独立、仍然 ready、可以绕过长延迟的工作。

### 内容要点

```text
load A      miss，等内存
add B       不依赖 A，可以先做
mul C       ready，可以先做
store D     等 A 回来后再提交
```

- OoO 适合未来依赖关系和地址在运行时才清楚的场景。
- 它用硬件 scheduler / rename / ROB 维持正确性和并行性。
- 但这些机制的面积、功耗和复杂度都很高。

### 转折句

AI 主干 kernel 里，很多 loop 边界、tensor shape、依赖关系和数据复用在编译期或 launch 前就能知道，因此不一定要靠硬件运行时猜。

## Slide 5. AI kernel 的敌人是数据太大

### 标题

The Granularity Changed

### 核心句

CPU 常常在管理几个 byte 或一个 cache line；AI kernel 常常在管理一个 tile 或一块矩阵。

### 内容要点

| 传统 CPU 程序 | AI 主干 kernel |
|---|---|
| 分支和地址经常运行时才知道 | shape / loop / stride 更可预测 |
| load/store 粒度小 | tile/tensor 粒度大 |
| 局部性由硬件 cache 透明发现 | 局部性可以由软件显式声明 |
| 追求低延迟和通用性 | 追求吞吐、复用和确定性 |

### 金句

当操作对象从几个 byte 变成一个 tile，局部性就不再只是 cache 的秘密，而可以成为编译器和 runtime 的计划。

## Slide 6. Transformer 改变了硬件问题

### 标题

From Sequence to Tensor

### 核心句

Transformer 把训练和 prefill 的大部分工作变成可并行矩阵计算，但 decode 仍然带来低 batch、KV cache 和动态控制问题。

### 内容要点

- Attention 让 token 间关系可以用矩阵计算表达。
- Prefill：输入 token 已知，可以较大程度并行。
- Decode：逐 token 自回归，时间维度串行。
- LLM serving 不是纯 GEMM，而是 GEMM + KV cache + vector/reduction + scheduling。

### 视觉

| 阶段 | 主要操作 | 硬件特征 |
|---|---|---|
| Prefill | Attention / FFN / GEMM | 高并行、高复用 |
| Decode | GEMV / KV cache read / sampling | 低 batch、访存重、动态控制 |

### 来源

- `transformer.md`
- `llm-inference-survey.md`

## Slide 7. Roofline 只问两个问题

### 标题

Two Roofs

### 核心句

Roofline 把性能上限压成两个问题：机器能算多快，数据能喂多快。

### 内容要点

```text
Performance <= min(Peak Compute, Bandwidth × Operational Intensity)
```

- 横线：峰值算力屋顶。
- 斜线：内存带宽屋顶。
- 交点 ridge point：memory-bound 和 compute-bound 的分界。
- 最终速度取决于更矮的那块屋顶。

## Slide 8. Operational Intensity 是复用能力

### 标题

OI Means Reuse

### 核心句

Operational Intensity 不是玄学，它就是每从 DRAM 搬 1 byte 数据，能做多少次计算。

### 内容要点

| Kernel | 数据复用 | 常见瓶颈 |
|---|---|---|
| memcpy / vector add | 很低 | 带宽 |
| GEMV | 中低 | 带宽 / cache |
| GEMM | 高 | 算力 / tile feeding |
| Attention | 混合 | memory + reduction + scheduling |

### 讲述重点

矩阵乘之所以适合 tensor core / systolic array，不只是因为它有很多乘加，而是因为 A/B tile 可以在近端被反复消费。

## Slide 9. 优化就是把点往右上推

### 标题

Move the Dot

### 核心句

架构和软件优化，本质上是在 roofline 图上把 kernel 往右、往上，或者换更高的屋顶。

### 内容要点

- 往右：blocking、tiling、layout、reuse，让同一份数据算更多次。
- 往上：提高带宽、减少 miss、prefetch、DMA、shared memory。
- 换屋顶：更大 tensor core / MXU / 更高峰值算力。
- 但如果 OI 不够，继续加矩阵单元可能只是让更多硅片等待数据。

## Slide 10. 数据搬运是 DNN 加速器的一等公民

### 标题

Memory Transfer Became the Workload

### 核心句

DNN 加速器的本质不是“做很多 MAC”，而是围绕 layer shape 设计 memory hierarchy、dataflow、precision 和 sparsity。

### 内容要点

- DNN 能耗很大一部分来自 off-chip DRAM，而不是 MAC。

- 降低精度、剪枝、MoE，也都可以理解为减少有效搬运或提高单位 byte 的计算量。

## Slide 11. Temporal vs Spatial

### 标题

Two Ways to Feed ALUs

### 核心句

Temporal 架构依赖硬件动态机制隐藏延迟；Spatial 架构让数据在 PE 附近停留并在 PE 间流动。

### 内容要点

- Temporal：CPU/GPU 更典型。ALU 从寄存器/cache 层次取数据，计算，再写回。
- Spatial：NPU/TPU 更典型。PE = compute + local state + control/data movement。
- Spatial 的收益来自数据复用更靠近计算单元。
- 代价是灵活性下降，需要 shape / mapping / compiler 配合。

### 视觉

```text
Temporal:
Cache/RF -> ALU -> Cache/RF
硬件负责猜局部性、隐藏延迟

Spatial:
PE <-> PE <-> PE
数据边流动边被消费
```

## Slide 12. Cache 是硬件猜局部性

### 标题

Hardware Discovers Locality

### 核心句

Cache 的价值是透明：程序员不用明确说数据放哪里，硬件自动把可能复用的 cache line 留在近端。

### 内容要点

- cache line 粒度搬运。
- tag / associativity / replacement 维护“有没有、放哪里、换谁”。
- prefetcher 继续猜未来地址。
- coherence 维护多核共享内存抽象。
- 非常适合不可预测、小粒度、低延迟、通用程序。

### 代价

- tag check、替换、冲突、容量 miss 都有成本。
- coherence 复杂。
- 硬件不知道未来，只能根据过去猜。

## Slide 13. Scratchpad 是软件声明局部性

### 标题

Software Declares Locality

### 核心句

Scratchpad / SMEM / VMEM 的核心是：软件或编译器明确告诉硬件，这个 tile 要搬进来、留多久、被谁消费。

### 内容要点

- 程序或编译器明确指定 HBM -> local memory。
- tile 算完之前不会被硬件透明替换掉。
- 数据搬运、同步、计算可以形成 producer-consumer pipeline。
- 没有 cache 的透明便利，但换来确定性、更低控制开销和更强复用控制。

### 对比句

Cache = hardware discovers locality.  
Scratchpad = software declares locality.

## Slide 14. 不是不要 cache，而是主战场变了

### 标题

Cache Did Not Disappear

### 核心句

现代 AI 加速器不是彻底不要 cache，而是把规则 tensor 主路径从“硬件猜”改成“软件排”。

### 显式管理更适合

- GEMM tile
- attention block
- conv tile
- weight / activation / partial sum
- HBM -> SMEM/VMEM/scratchpad -> tensor core

### cache 仍然适合

- metadata
- 不规则 gather/scatter
- CPU 控制流
- KV cache 动态管理中的部分路径
- 跨 kernel / 跨 operator 复用
- 系统软件、runtime、调度

### 关键句

局部性没有消失，只是从 cache-line 粒度提升到 tensor/kernel/stream 粒度。

## Slide 15. DianNao：早期答案已经出现

### 标题

Before TPU, There Was Scratchpad

### 核心句

DianNao 很早就指出：对规则 DNN 访问，通用 cache 的 tag、associativity、speculative read 和 conflict 可能变成额外成本。

### 内容要点

- DianNao 用 NFU + NBin/NBout/SB + DMA 组织前向推理。
- 它不依赖传统 cache，而是用软件管理 buffer / scratchpad 保存输入、权重和部分和。
- DMA 预取相当于非投机 prefetch：提前把确定会用的数据搬到近端。

## Slide 16. Systolic Array：数据在 PE 间流动

### 标题

Compute Stays, Data Moves

### 核心句

脉动阵列的重点不是“很多 MAC”，而是 A/B 元素在二维阵列中传播并被重复消费。

### 内容要点

- A 沿行传播，被同一行多个 PE 复用。
- B 沿列传播，被同一列多个 PE 复用。
- 每个 PE 做简单 MAC，不需要复杂指令调度。
- 代价是 shape、padding、mapping 更重要。

### 视觉

3x3 PE 网格 + A/B 流向。

## Slide 17. GPU 不是没有动态性，而是用海量线程隐藏延迟

### 标题

Throughput Hides Latency

### 核心句

CPU 靠复杂单线程机制隐藏延迟；GPU 靠大量 warps、occupancy 和吞吐调度隐藏延迟。

### 内容要点

| CPU | GPU |
|---|---|
| 少量复杂 core | 大量 SM / lane |
| 强单线程、低延迟 | 高吞吐、海量并行 |
| OoO / BPU / cache 复杂 | warp scheduling / occupancy |
| 适合不可预测控制流 | 适合规则并行数据流 |

### 衔接

Tensor Core 出现后，GPU 在保留线程生态的同时，开始把矩阵主干交给更专门的执行路径。

## Slide 18. GPU 从线程吞吐走向显式数据移动

### 标题

GPU Also Moves Toward Dataflow

### 核心句

GPU 仍然是线程生态，但高性能路径越来越像 dataflow pipeline。

### 内容要点

- A100：`cp.async`，把 global memory 直接搬到 shared memory。
- H100：TMA 描述 tile 形状、stride、目的地，硬件搬整块数据。
- H100：mbarrier 支持 producer-consumer pipeline。
- H100：WGMMA 让 tensor core 直接消费 shared memory。
- B200：TMEM / tcgen05 进一步把 tensor compute 与 warp 调度解耦。

## Slide 19. TPU：从第一天起押注编译器

### 标题

Compiler First

### 核心句

TPU 放弃很多动态机制，用 MXU、VMEM 和编译器调度 DMA 换取密度、确定性和规模化。

### 内容要点

- MXU 是矩阵主干。
- VMEM 是软件管理的近端 memory。
- 编译器负责 HBM -> VMEM -> MXU/VPU regfile 的数据路径。
- 好处：吞吐密度、确定性、大规模互联。
- 代价：shape、padding、动态 workload、escape hatch。

## Slide 20. GPU/TPU 收敛：不同路，同一堵 memory wall

### 标题

Different Roads, Same Wall

### 核心句

GPU 越来越显式地管理数据流；TPU 一开始就把数据流交给编译器。两者都在承认：data movement 是架构一等公民。

### 对比

| GPU | TPU |
|---|---|
| 从 SIMT 灵活性出发 | 从矩阵 dataflow 出发 |
| 逐步显式化数据移动 | 编译器一直调度数据移动 |
| SMEM / DSMEM / TMEM | VMEM 是核心层 |
| CUDA / Triton escape hatch | Pallas / Mosaic / XLA |
| 生态和调试强 | 吞吐密度和确定性强 |

## Slide 21. Tile 是现代 AI 编程的核心抽象

### 标题

Think in Tiles

### 核心句

Tile 卡在一个很关键的抽象层：比 whole operator 更可控，比 lane/warp/instruction 更可移植。

### 内容要点

- Whole op：matmul / attention / conv，表达简单，但难做特殊融合和局部优化。
- Tile：固定形状数据块，能表达数据复用、片上缓存、Tensor Core/MXU 使用。
- Instruction：mma / wgmma / load / barrier，控制力最强，但负担极大。

## Slide 22. 软件栈为什么成为架构的一部分

### 标题

Compiler as Architecture

### 核心句

在 AI 加速器里，编译器/runtime 不只是翻译代码，而是在决定 tile shape、layout、fusion、DMA、buffer residency、barrier 和 MMA/MXU schedule。

### CPU 类比

- CPU 编译器主要生成 load/store/branch，很多动态调度交给硬件。
- AI accelerator 编译器需要把数据移动和计算流水线一起排好。
- 硬件越确定，软件栈越需要知道机器结构。

### 金句

软件栈成为机器的一部分，不是口号，而是因为数据路径本身已经被软件编排。

## Slide 23. NVIDIA stack 示例：软件栈到底是哪几层

The NVIDIA Stack

### 核心句

不同层暴露不同粒度的控制权：越往下，控制越强，程序员负担越重。

- CUDA：threads、warps、blocks、SMEM、barrier、TMA 等硬件可见编程模型。
- PTX / SASS：虚拟 ISA 和机器码，通常不用直接碰，除非追极限性能或 debug。

## Slide 24. 一次 tile kernel 是怎么被编排的

### 标题

Scheduling a Tile Pipeline

### 核心句

软件编排不是简单“调用下层库”，而是在安排数据什么时候到、放在哪里、谁等待谁、计算和搬运如何重叠。

### 流程

```text
PyTorch op / torch.compile
  -> Triton kernel: BLOCK_M / BLOCK_N / BLOCK_K
  -> compiler chooses layout + stages
  -> runtime launches grid
  -> HBM -> SMEM via cp.async / TMA
  -> mbarrier sync
  -> WGMMA / Tensor Core consume
  -> store back
```

### 讲述重点

高性能 kernel 的核心不是“写一个 for 循环”，而是让 load、barrier、MMA、store 形成稳定 pipeline。

## Slide 25. GPU vs TPU 软件栈边界不同

### 标题

Where the Boundary Lives

### 核心句

GPU 和 TPU 都在做 tile/dataflow，但它们把复杂度放在不同的软件层。

### 对比

| GPU / NVIDIA | TPU / Google |
|---|---|
| PyTorch + CUDA/Triton 生态强 | JAX/Pallas/XLA 组合性强 |
| Triton/CUDA/CUTLASS 是重要 escape hatch | Mosaic 接管 layout、DMA、VLIW |
| 调试、快速迭代、第三方库强 | 编译器统一优化、确定性、规模化强 |
| 复杂度更多暴露给 kernel author | 复杂度更多交给 compiler |

## Slide 26. Timeloop：mapping 决定硬件是否真的快

### 标题

Mapping Is Performance

### 核心句

同一个硬件，在不同 tiling、loop order、dataflow 和 bypass 策略下，性能和能耗可能差很多。

### 内容要点

- mapping 决策：tiling、loop permutation、spatial partitioning、temporal scheduling、bypass、dataflow constraints。
- Timeloop 把“硬件描述 + workload + mapping constraints”变成可搜索的 mapspace。
- 性能/能耗模型本质是结构化 roofline / bottleneck model。

### 对 AME 的启发

不能只建矩阵单元 ops/cycle，还要建数据如何被搬、复用和等待。

### 来源

- `timeloop.md`

## Slide 27. LLM serving 不是纯 GEMM 世界

### 标题

Prefill Loves Matrix, Decode Loves Systems

### 核心句

Prefill 更像规则大矩阵计算，decode 更像低 batch GEMV + KV cache + 动态控制，因此加速器必须和 CPU/系统调度协同。

### 内容要点

| 部分 | 操作 | 并行性 | 风险 |
|---|---|---|---|
| Prefill FFN | 大 GEMM | 高 | 喂饱矩阵单元 |
| Attention | GEMM + softmax | 中高 | reduction / SRAM 复用 |
| Decode | GEMV / 小 batch | 低 | 大阵列利用率 |
| KV cache | read/write/gather | 低 | 容量、带宽、metadata |

### 视觉

- `images/15-prefill-decode.png`
- `images/15-kv-cache.png`

### 来源

- `llm-inference-survey.md`

## Slide 28. Prefill / Decode 的瓶颈差异

### 标题

Same Model, Different Bottlenecks

### 核心句

同一个 LLM，在 prefill 和 decode 阶段对硬件的要求很不一样。

### 内容要点

- Prefill：大矩阵、batch/token 并行、高复用，适合矩阵单元。
- Decode：逐 token、小 batch、KV cache 读写重，容易 memory/system-bound。
- Attention：既需要矩阵，也需要 softmax/reduction/vector。
- Sampling / routing / metadata：CPU 或灵活控制仍然重要。

### 对 XSAI 的问题

如果只围绕大 GEMM 设计 AME，可能会低估 decode、KV cache 和 vector/reduction 的系统成本。

## Slide 29. XSAI 当前坐标

### 标题

Where XSAI Sits Today

### 核心句

当前 XSAI 更像 CPU 紧耦合矩阵扩展的起点：大 OoO core 搭配 CUTE 类 tensor core，共享 L2Cache，但还没有完整 scratchpad/dataflow 软件栈。

### 内容要点

- 大 OoO core：控制流、通用程序、低延迟调度。
- CUTE：类 tensor core，负责矩阵主干。
- 共享 L2Cache：当前主要数据供给路径。
- 暂无独立 scratchpad 模式。
- 暂无独立 vector/reduction 模块。
- AME 指令和 runtime 边界还很早期。

### 视觉

- `images/16-xsai.png`

### 讲述重点

这页不要做强结论，只讲“我们当前坐标”。强调它不是完整 TPU-like dataflow accelerator，而是一个 CPU 紧耦合 AME baseline。

## Slide 30. AME 的核心问题：谁拥有这块 tensor？

### 标题

Who Owns the Tensor?

### 核心句

对 CPU 紧耦合 AME 来说，难点不是单纯加 scratchpad，而是 tensor 数据在 CPU cache、L2、AME local memory 之间的 ownership 和切换成本。

### 双路径

```text
Path A:
HBM -> AME scratchpad -> CUTE
适合大 GEMM / prefill / 规则 tile

Path B:
HBM -> shared L2 -> CPU vector + AME
适合动态控制 / 小 batch / norm / softmax / metadata
```

### 关键问题

- 这块 tensor 在某段时间内归 CPU cache 管，还是归 AME scratchpad 管？
- 切换 ownership 需要 flush / invalidate / fence / DMA sync 吗？
- 中间结果如果在 CPU vector 和 AME 之间来回走，会不会比算得快更重要？

### 来源

- `GPU-vs-TPU-software.md`
- `XSAI.md`
- `AME-vs-IME.md`

## Slide 31. AME vs IME 不是名字之争

### 标题

Where Does Matrix State Live?

### 核心句

AME vs IME 的本质问题是矩阵状态住在哪里、数据路径从哪里来、软件栈暴露到什么粒度。

### 对比

| 路线 | 矩阵状态 | 优势 | 风险 |
|---|---|---|---|
| RVV | vector registers | 通用、生态连续 | 指令数多，矩阵复用弱 |
| IME | VRF + matrix FU | ISA 连续，集成成本低 | VRF 容量、load bandwidth、端口压力 |
| AME | dedicated matrix side | 更容易重做数据路径 | matrix/vector 边界、一致性、软件栈 |

### 讲述重点

SpacemiT K3/A100 这种 IME-like 高性能方案，最后也会碰到超宽 VRF、load channel、多个 core 供一个 tensor core、local memory、AI-DMA 和 async prefetch。

---

## Slide 32. 下一步不是先做复杂，而是先量清楚卡在哪里

### 标题

Measure Before Adding Hardware

### 核心句

Scratchpad、DMA、vector 模块、更多 AME 指令都可能有价值，但应该由 workload 和 gem5 数据推动。

### 要量的问题

- Shared L2 是否够喂 CUTE？
- tile setup latency 是否吞掉收益？
- batch=1 / 小 batch decode 是否被 KV cache 和 matrix/vector 边界主导？
- 是否需要 AME scratchpad/local memory？
- softmax / norm / RoPE / activation 放 CPU vector 还是 AME 侧？
- 是否需要 DMA / async prefetch / software-managed tile movement？

### 指标

- CUTE utilization
- load stall / memory stall
- L2 bandwidth
- working-set residency
- sync overhead
- matrix/vector boundary copies
- prefill / decode split

## Slide 33. 三条 Takeaways

### 标题

Data Moves. Compiler Plans. AME Measures.

### Takeaway 1

Data movement is the architecture.  
算力不是孤立指标，数据路径决定矩阵单元能不能被喂饱。

### Takeaway 2

Compiler/runtime is part of the machine.  
tile、mapping、DMA、layout、sync 的决策越来越前移到软件栈。

### Takeaway 3

XSAI/AME should evolve by evidence.  
当前 OoO + CUTE + shared L2 是合理起点；scratchpad、vector 模块、DMA 和更多指令，需要由 workload 与 gem5 数据推动。

## Slide 34. 组内讨论问题

### 标题

Open Questions

### 问题

1. XSAI 的 AME 应该长期依赖 shared L2，还是需要独立 scratchpad/local memory？
2. softmax、layernorm、RoPE、GELU/SiLU 这些 vector/reduction 操作应该交给 CPU/RVV，还是放进 AME 侧？
3. 如果加入 DMA/async prefetch，ISA/runtime 应该暴露到 tile、stream 还是更细？
4. 如何公平做 IME-like baseline：固定算力、VRF/L1/L2/load BW 后比较？
5. 哪些 kernel 应该先量：batch=1 decode、small-batch GEMM、attention、norm/softmax 混合链路？

### 收束句

先量数据，再加硬件。避免把所有趋势一次性塞进 XSAI，先让 workload 告诉我们最该建模和扩展的部分。
